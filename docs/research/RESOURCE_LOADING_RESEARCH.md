# 资源加载优化调查

适用 MHW:I 15.23 / Steam build 15539686，VA基址0x140000000。2026-11-16。用户报告第二版将进入任务时间从约30秒降到13秒；尚未收到第二版完整日志，不能确定剩余13秒中资源加载的占比，也不能把全部差值归因于同一计时补丁。

本轮经项目stdio MCP查找函数、调用关系与符号，再以Ghidra只读反编译核对。未改动第二版DLL或源代码。原始日志在本聊天work/resource-load.log、resource-queue.log、resource-engine.log、resource-cache.log。

## 1. 普通ticket之间有串行提交约束

141B80820只是把DTI与路径加入ticket，尚未真正提交资源加载。141B80C70写入加载flags（启动调用通常为2），并把ticket状态设为1。

141B80F30的更新循环调用141B811B0。后者使用manager+A240保存当前普通ticket；只有该指针为空才扫描其他待处理ticket，并按ticket+1C（manager+54+index*28）数值选择。当前ticket的state1遍历其全部资源，调用sMhResource的LoadResource；state2检查每个resource+64 bit0，未全部就绪就保留当前ticket并返回。当前ticket完成后才清当前指针，继续下一ticket。

因此：一批内部可一次提交多个资源，但不同普通ticket之间存在“前批未完成，后批未提交”的限制。A248是另一个特殊通道，来自提交参数的末尾布尔标志，不能把它当成通用安全并发开关。

优化候选：对已知独立的启动资源提前发起原生异步请求，使后续ticket命中已注册对象；或在完成依赖审计后合并特定批次。不能直接全局清A240、改变ticket状态或重入执行loader。

## 2. 原生异步加载和缓存已存在

1422228D0 sMhResource::loadResource按flags分派：bit1（数值2）进入142224D50 TryLoadFile2，bit0（数值1）进入142224FA0 TryLoadFile。

142224D50先按资源ID查表/FindLoadedInstance；已存在就增加引用并返回。新对象注册后入队并ReleaseSemaphore。这证明启动ticket的flags=2已经使用排队加载，不能假设目前全部同步，更不能声称多次请求同一路径就是重复读盘。

142224FA0也复用已有对象；若另一执行者尚未完成加载，会在resource ready位上Sleep(1)轮询。该Sleep是实际完成等待，并非可删除的固定显示延迟。把同步请求改成异步后直接交给使用者会暴露未完成对象；正确优化需将请求提前，并仍在消费前等待完成。

实际工作线程数、磁盘/解压/GPU上传各自耗时，本轮未确定。

## 3. 标题画面虽然被跳过，相关资源仍预载

14025DA80的state0组装第一批资源：GUI组5、根据存档进度选择的stage/title调度器、ui/save_icon/save_pos、sound/env/title/title_envb、common/title/title_news、本地化title_news文本、common/ui/staffRollDataSlugger，以及ui/credit/tex/logo/logo_...纹理。state1等待整批完成，之后还等声音状态与GUI准备。

这比“完全替换初始化”更具体：可审计自动进任务路径是否真的需要news、credits和标题场景，并逐项去掉无用请求或推迟到返回标题时加载。

但当前不能直接删除整批：存档图标仍被aTitle使用；14025EF60会再次获取标题调度器并构造scheduler；标题初始化还会获取title_envb绑定声音对象。缓存命中与资源引用生命周期必须保留。新闻/credits也尚未逐一追完消费者。

## 建议实验顺序

1. 用第二版完整日志区分启动执行阶段与进入任务后的场景加载。现有aTitle execute日志不包含此前14025DA80资源准备内部阶段，不能把两者混同。
2. 仅为启动相关ticket记录提交、首次真正发出请求、完成的时间，以及资源数量/未就绪资源路径；记录到内存缓冲，阶段结束再输出，避免逐资源同步文件日志影响测量。
3. 如果大量时间在排队：小范围提前请求/重叠独立批次，并持有引用到原生消费者接管。优先固定的公共GUI/文字资源，语言配置须已确定；任务场景预加载则需另外确认任务/地图依赖。
4. 如果时间主要在标题专用资源：先审计news/credits消费者，再做逐项裁剪实验，验证首次启动、失败回退及返回标题。
5. 暂不盲目增加线程或改优先级。已有后台队列可能受其他环节限制；更多并发可能增加竞争，必须根据数据决定。

结论：资源层确有可操作的研究方向，最明确的是“让独立请求更早进入已有异步加载队列”和“减少自动任务路径不需要的标题资源”。尚无实测收益或可直接发布的资源加载补丁。

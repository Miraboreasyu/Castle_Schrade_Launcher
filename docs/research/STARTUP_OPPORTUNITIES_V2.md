## 1. 最明确的低侵入候选：增加常驻构建预算

`141B7BFE0` state4 依次调用 `141373CC0`、`140279080`、`140BD3B50`、`140BCD4E0`。前一个未完成就返回，后面的构建器该帧不会运行。

`141373CC0` 自身是分阶段构建器，其阶段2调用 `141373E40`。后者对两个 CraftElement 数据表分别使用 `idx - savedCursor > 100` 限额：每次最多处理101条，然后保存游标、返回未完成。它不是异步 I/O 等待。另三个构建器也把索引构建拆成多个调用阶段，但本次检查的函数没有同样的101条限额。

候选实现：只在首次 Logo 的 resident state4 内，为原生构建增加每帧调用预算，例如在小时间预算和最大调用次数限制内重复推进。保持原生顺序、游标、结束条件和全部索引数据。先测单次构建耗时，再确定预算；时间预算不能中断一个已经进入的原生调用。

该方案目标是减少空等到下一帧的时间。0.687秒是这一整个阶段的现有跨度，不是承诺能省下的时间。无需首先引入新线程；不同构建器是否可真正跨线程同时执行仍未证明。

## 2. 并行化的实际边界：普通加载队列只有一个原生工作线程

新增静态证据：

- `14221FDD0` 创建一个 `Loader 1`，句柄保存在资源管理器 `+208090`；另建一个 `InterceptLoader 1`，保存在 `+211110`。这里没有按核心数创建普通线程池的循环。反编译器对该函数的 TypeInfo::ctor 命名不准确，判断依据是函数体。
- 普通线程虚表 `1435043F8 +28h` → `1422243E0` → `1422255F0`；特殊线程虚表 `143504428 +28h` → `1422243A0` → `142220F40`。
- 普通线程依次从 `+2080A0` 队列取一个资源，在队列锁外调用 `142225420`，完成后才取下一个。特殊线程使用另一组队列及锁。
- `142225420` 打开资源流，调用该资源虚表的反序列化和完成方法，再设置完成位。因此这里的“加载”不只是拷贝文件字节。
- 普通 ticket 的 `141B811B0` 还会保持 `manager+A240` 为当前批次，直到当前批次完成才选择下一批。这是工作线程之上的另一层串行限制。

由此可确认：异步不等于普通资源彼此并行；现有预加载主要实现了加载与主线程其他工作的重叠。资源内部、压缩包和渲染系统是否另有并发，不在上述结论范围内；其他 mod 是否修改线程创建也未动态验证。

最先可尝试的是提前提交经过依赖核对的资源，利用主线程构建、存档 I/O 或联网期间的窗口。直接增加 Loader 线程、把所有请求改到 Intercept 队列，需要额外审计资源类型、递归依赖、线程索引、停止/回收和第三方 hook。队列锁存在只证明入队/出队有保护，不证明所有资源初始化可并发。暂不把它作为低风险补丁。

两个 loader 中的 `Sleep(10)` 都在暂停/忙标志成立时轮询；信号量等待是等真实工作。不能按固定展示计时处理。未发现“每加载一个资源都无条件睡眠10ms”的行为。

## 3. 与建房重叠的地图预加载：有入口，但上下文还不齐

`14024FB60` 为据点选择资源 ticket；通过 `141670EC0` 转换区域编号，再调用 `1418AB200` 组装请求。它还处理房间对应的据点、当前节庆，以及 Astera 的额外 NPC 对象请求。

`1418AB200` 并非只依赖传入的编号：先经 `141AC0B10(sMhArea)` 读取当前区域描述，再选择 scheduler、碰撞、导航、灯光、遮挡、物件、音频等不同类型，并应用场景变体。

因此不能在标题期间仅调用 `1418AB200(ticket, savedAreaIndex, 1)` 就期待获得目标区域的正确资源清单，也不应提前篡改全局当前区域来骗取清单。

后续可做的独立实验：为已确认目的地解析一小组与节庆/剧情无关的静态资源，持有原生资源引用，和真实 session 创建并行；正式场景入口仍请求完整资源并等待完成。先给 aLoader/区域就绪增加时间点，才能评估最终可操作时间的收益。旧样本中2.125秒的建房区间只是可能的重叠窗口。

## 4. 字体阶段：异步 ticket 完成并不代表字体初始化结束

Logo state16h 先请求语言相关 `residentChars_s*` / `residentChars_s*_df` 数据；完成后设置配置对象 `+7B700=0`。配置应用 `140FBA4F0` 看到状态0或5时会调用 `141AD9800`。

`141AD9800` 重置两套字体缓存，按语言选择六个字体槽，使用 flags=1 获取 rGUIFont，再调用 `1426F8080` / `1424DA090` 处理字符数据。入口也由主程序构造流程调用。这条链说明日志中“font ticket ready”之后仍可能有同步字体获取和缓存构建。

候选：语言确定后提前请求对应 rGUIFont，让配置应用命中缓存；或确认语言、字体实例和渲染状态均未变时避免重复缓存构建。后者条件复杂，不能只比较语言编号；还未证明0.484秒空档具体有多少由这些调用占用。

## 5. 进一步裁剪资源的结论

没有找到另一组像制作人员表一样、消费者可一起安全省略且收益明确的加载项。

- 标题新闻和 title_envb 有正常标题初始化消费者；仅从 ticket 删除会转成同步获取。要裁剪需连同对应 GUI/声音绑定和恢复路径一起处理，当前标题批次已就绪，优先级较低。
- 常驻批次的463个固定描述符在 state3 又以同步接口取得并安装到全局引用。删除预载条目通常会把工作推迟到该阶段；取消全局绑定则会影响后续消费者。
- `141B7CD80` 还枚举 `quest/bui` 并请求大量 remData。条目多不等于冗余，未证明其消费者支持延迟加载；当前不能安全按目标任务删掉其他条目。
- 相同 DTI/路径再次请求通常复用资源管理器已有对象并增加引用，不能用调用次数估算重复磁盘读取。

## 推荐实验顺序

1. 为常驻构建器记录耗时/调用次数，并试验首次启动内提高构建预算；最明确、改动范围最小。
2. 分解配置应用/字体缓存重建耗时，按实际耗时决定字体预加载是否值得。
3. 给建房后到地图可操作的路径补充测量，再试一小组目标地图资源与建房重叠。
4. 全局资源线程扩容、Intercept 通道泛化和常驻资源删除暂缓。
